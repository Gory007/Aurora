# Роадмап PoC-рации (простая версия) — этапы разработки

Для созвона: что делаем, что изучаем и зачем. Знакомство с SDK пропущено — сразу разработка.

---

## Этап 1. «Мозг» рации — логика захвата эфира ✅ (готово)
**Что делаем:** пишем правила: кто сейчас может говорить, а кто ждёт. Как в настоящей рации —
в эфире говорит только один.
**Что изучить:** Qt Signals & Slots (способ, которым части программы «зовут» друг друга:
один объект кричит «изменилось!», другие на это реагируют).
**Зачем:** без этой логики дальше нельзя — всё приложение строится вокруг состояния
«свободен / говорю / слушаю».

## Этап 2. Связь с сервером — «кто онлайн и кто говорит» ✅ (готово, прототип)
**Что делаем:** приложение по интернету обменивается короткими текстовыми командами
с сервером: «я подключился», «хочу говорить», «отпустил эфир».
**Что изучить:** TCP-сокеты (QTcpSocket) — «телефонный провод» между программами;
JSON — формат коротких сообщений.
**Зачем:** рация работает не напрямую «телефон-телефон», а через сервер-диспетчера.
Мы уже проверили: два клиента подключаются, первый занял эфир, второму отказано.

## Этап 3. Кнопка и экран (QML UI) ⬜ следующий
**Что делаем:** большой экран со статусом и одна огромная кнопка PTT (Push-To-Talk —
«нажал—говоришь, отпустил—слушаешь»). Плюс список участников.
**Что изучить:** QML — язык описания интерфейса в Qt (пишется как простые теги),
свойства MODEL/VIEW (данные сами «перетекают» из C++ в список на экране).
**Зачем:** чтобы логику можно было нажать пальцем и показать комиссии работающее приложение.

## Этап 4. Звук: микрофон → сжатие → передача ⬜
**Что делаем:** ловим звук с микрофона, сжимаем его кодеком Opus (как mp3, но для голоса),
режем на маленькие кусочки по 20 мс и отправляем.
**Что изучить:** GStreamer (конструктор: цепочка блоков «микрофон → кодек → сеть»),
понятие «потоковое аудио» и задержки.
**Зачем:** это сердце рации. Без звука предыдущие этапы — просто «умный пинг».
Это самый рискованный этап, поэтому каркас делали сначала без звука.

## Этап 5. Звук: приём и воспроизведение + «эфир занят» ⬜
**Что делаем:** второй телефон распаковывает Opus и играет голос в динамик; добавляем
короткий «клик/гонг» начала и конца речи (как у настоящих раций).
**Что изучить:** джиттер-буфер (почему речь не «заикается», когда пакеты приходят с перебоями).
**Зачем:** двусторонняя связь — продукт становится usable.

## Этап 6. Сервер по-настоящему (Python, WebSocket) ⬜
**Что делаем:** заменяем учебную заглушку настоящим сервером: держит список участников,
раздаёт эфир одному, ретранслирует голос всем остальным.
**Что изучить:** WebSocket (постоянное двунаправленное соединение), asyncio в Python.
**Зачем:** на телефоне нет «белого списка» входящих портов — соединения всегда инициирует
телефон наружу, поэтому сервер обязателен.

## Этап 7. Работа в фоне и уведомления ⬜
**Что делаем:** рация продолжает слушать эфир, даже когда свернута; уведомление «говорят».
**Что изучить:** жизненный цикл приложения Авроры (заморозка при сворачивании),
DBus-уведомления, LockManager (не давать телефону уснуть во время разговора).
**Зачем:** рация, которая умирает при сворачивании, — не рация. Это «авроро-специфичная»
часть, которую ценят на защите.

## Этап 8. Сборка .apm и установка на устройство ⬜
**Что делаем:** упаковываем в формат приложений Авроры (.apm: манифест, иконки, qml-модуль),
ставим на тестовый телефон/эмулятор.
**Что изучить:** spec-файл и mb-build (сборка через Sailfish SDK), структура каталогов Авроры.
**Зачем:** демо на реальном устройстве = главный аргумент на защите.

## Этап 9. Красота и запасной план ⬜
Громкость, шумоподавление, запись переговоров, группа/каналы, тесты, README для отчёта.

## Архитектура (для демонстрации)

```
┌─────────────── Телефон A (наше приложение) ───────────────┐
│                                                            │
│   UI (QML)          Логика (C++)            Сеть/Аудио     │
│   ┌─────────┐      ┌──────────────┐        ┌────────────┐  │
│   │ кнопка  │─тап─▶│ RadioState   │◀──────▶│ Signaling  │──┼──┐
│   │ PTT,    │      │ (свободен/   │ сигна- │ Client     │  │  │
│   │ список  │      │  говорю/     │  лы    │ (TCP/JSON) │  │  │
│   │ участников│    │  слушаю)     │        └────────────┘  │  │
│   └─────────┘      └──────┬───────┘        ┌────────────┐  │  │
│                           │                │ AudioEngine│──┼──┤ Интернет
│                           └───────────────▶│ (GStreamer │  │  │
│                                            │  + Opus)   │  │  │
│                                            └────────────┘  │  │
└────────────────────────────────────────────────────────────┘  │  │
                                                                ▼  ▼
                                                ┌──────────────────────────┐
                                                │  Сервер (Python)         │
                                                │  • кто в сети            │
                                                │  • кому можно говорить   │
                                                │  • ретрансляция голоса   │
                                                └──────────────────────────┘
```

Два потока данных:
1. **Сигнальный (короткие команды):** «занять эфир», «эфир свободен», список участников.
2. **Аудиопоток (голос):** маленькие кусочки Opus-звука, летят только тому, кто «в эфире слушает».

## Где посмотреть код (папка poc-radio/)

| Файл | Что там | Простыми словами |
|---|---|---|
| `src/radiostate.h/.cpp` | класс RadioState | «Мозг»: переключает состояния, решает, можно ли говорить |
| `src/signalingclient.h/.cpp` | класс SignalingClient | «Почтальон»: читает/пишет JSON-команды по TCP |
| `src/main.cpp` | точка входа | собирает всё вместе, параметры запуска |
| `tests/mock_server.py` | учебный сервер | имитирует настоящий сервер для проверки |
| `poc-radio.pro` | проект qmake | «рецепт» сборки: какие файлы компилировать |
| `README.md` | инструкция | как собрать и запустить проверку |

Как проверить своими руками (на ПК с Qt5):
```
cd poc-radio
qmake && make                         # собираем приложение (один раз)
python3 tests/mock_server.py &        # в терминале 1 запускаем учебный «сервер»
./poc-radio --server 127.0.0.1 --port 5000   # в терминале 2 — клиент «Петя»
# через 3 сек он займёт эфир; повторите запуск вторым терминалом —
# второй клиент получит "эфир занят" и не сможет говорить
```

## Полная архитектура (расширенная схема для демонстрации)

```
                 СИГНАЛЬНЫЙ ПУТ (короткие команды, TCP/JSON)
   Телефон A ──────────────┐                      ┌────────────── Телефон B
                           ▼                      ▼
                  ┌─────────────────────────────────────┐
                  │        СЕРВЕР (Python)              │
                  │  Registry: кто в каком канале       │
                  │  FloorManager: кому разрешено       │
                  │              говорить (один!)       │
                  │  Relay: пересылает голос слушателям │
                  └──────────────┬──────────────────────┘
                                 ▲
                 АУДИОПУТЬ (кусочки Opus по 20 мс, UDP/RTP)
   Микрофон A → [GStreamer: capture→opusenc→rtp] ══▶ сервер ══▶ [rtp→opusdec→speaker] → Динамик B

   Внутри телефона (слои, сверху вниз):
   ┌───────────────────────────────────────────┐
   │ UI-слой (QML): кнопка PTT, статус, список │  ← этап 3
   ├───────────────────────────────────────────┤
   │ Логика (C++): RadioState — «мозг»         │  ← готово ✅
   ├───────────────────────────────────────────┤
   │ Сервисы (C++): SignalingClient, AudioEngine│ ← частично ✅
   ├───────────────────────────────────────────┤
   │ Платформа Авроры: LockManager, DBus-уведом-│ ← этап 7
   │ ления, жизненный цикл (freeze при сворач.) │
   └───────────────────────────────────────────┘
```

Почему именно так (одним предложением для защиты): сигнализация и звук разделены,
потому что команды должны надёжно доходить (TCP), а голос — быстро и с потерями лучше,
чем никак (UDP); сервер нужен, потому что телефоны за NAT не принимают входящие соединения.
