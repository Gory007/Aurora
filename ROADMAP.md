# Роадмап: PoC-рация для ОС Аврора (Qt/C++, Aurora SDK)

Приложение — рация Push-to-Talk поверх интернета (PoC) на смартфоне/планшете с ОС Аврора.
Стек: Qt 5 + C++, Aurora SDK, qmake, деплой через .apm.

---

## Этап 0. Подготовка окружения (1–3 дня)

**Цель:** собрать и запустить «Hello World» на устройстве.

- [ ] Установить Aurora OS SDK (официальный дистрибутив от Открытой Мобильной Платформы).
      SDK включает: Qt 5 с патчами Авроры, компилятор (gcc), qmlformat, утилиты `aab`, `apm-tool`,
      Emulator (на базе Android/x86 или нативный эмулятор Авроры).
- [ ] Изучить структуру типового проекта Авроры:
  ```
  poc-radio/
  ├── poc-radio.pro          # qmake-проект
  ├── src/                   # C++ код
  ├── qml/                   # QML интерфейсы
  ├── po/                    # переводы (.ts)
  ├── icons/                 # иконки приложений
  ├── rpm/                   # spec-файл для сборки .apm (опционально)
  └── *.desktop              # десктоп-файл приложения
  ```
- [ ] Пройти базовый туториал Aurora SDK: создание Application Template, запуск на эмуляторе.
- [ ] Настроить отладку на реальном устройстве по ADB (Aurora Developer Mode + SSH/ADB).
- [ ] Разобраться с жизненным циклом приложения Авроры:
      - приложение живёт в **window-режиме** (одна или несколько окон — `Application` из `sailfish.app`);
      - при сворачивании в фон процесс может быть **заморожен** (frozen state) — критично для рации!
      - сигналы `application.stateChanged`, состояния `Active / Activating / Deactivating / Frozen`.

**Результат этапа:** пустое приложение стартует на эмуляторе и реальном устройстве,
корректно переживает сворачивание/разворачивание.

## Этап 1. Знакомство с платформенными API Авроры (2–4 дня)

**Цель:** понять, чем Аврора отличается от десктопного Qt.

- [ ] Модуль `sailfish.application` — управление окнами, lifecycle, `QtSingleApplication`-подобное поведение.
- [ ] `native::LockManager` (`sailfish.native`) — **keep-locks**: не даём системе уснуть/заморозить
      приложение во время приёма вызова (аналог wakelock в Android). Без этого фоновая рация неработоспособна.
- [ ] Медиа-сервисы Авроры: `sailfish.mediaservice` (MediaService, AudioProfiles) — маршрутизация звука,
      гарнитура, Bluetooth-гарнитуры.
- [ ] `sailfish.settings` / `native::NetworkManager` — мониторинг состояния сети (Wi-Fi/LTE, роуминг).
- [ ] Уведомления: `native::NotificationManager` + `NativeMessage` — входящий PTT-вызов при свернутом приложении.
- [ ] Доступ к микрофону: проверка разрешений; на Авроре микрофон даёт GStreamer/ PulseAudio —
      проблем с permission-моделью как в Android обычно нет, но проверить на целевой версии ОС.
- [ ] Форм-фактор UI: Аврора — это **QML + Compositor**. Базовые компоненты:
      `Sailfish.Page`, `Sailfish.PageRow`, `HarmonyIcon`, темы light/dark, масштабирование под планшеты.

**Результат этапа:** прототип UI из 2 страниц (главная + страница канала), приложение держит
keep-lock и показывает тестовое уведомление из фона.

## Этап 2. Архитектура приложения (2–3 дня)

**Цель:** спроектировать скелет, чтобы потом не переписывать.

- [ ] Слой-модель:
  ```
  QML (UI)  <->  C++ backend (QObject-синглтоны через qmlRegisterType / context property)
                    ├── SessionManager   — состояние PTT-сессии (idle/listening/talking)
                    ├── SignalingClient  — WebSocket/JSON: регистрация, каналы, presence
                    ├── MediaTransport   — RTP-стрим (отправка/приём аудио)
                    ├── AudioEngine      — GStreamer pipeline: capture/mix/playback
                    ├── NetworkMonitor   — сеть, reconnect, offline-логика
                    └── SettingsStore    — QSettings (сервер, позывной, каналы)
  ```
- [ ] Конвейер состояний PTT: `IDLE → LISTENING → PRESSTX(TRANSMITTING) → RECEIVING → IDLE`
      с явной моделью на одном QObject + `Q_ENUM` + сигналы в QML.
- [ ] Выбор протокола сигналализации: WebSocket (RFC 6455) + JSON-команды
      (`join_channel`, `ptt_begin`, `ptt_end`, `channel_list`, `presence`).
- [ ] Решение по транспорту аудио (см. Этап 3): Opus поверх RTP/UDP или готовый стек (Linphone/ortp, oboe-аналога нет).
- [ ] Структура Git: ветки `dev/main`, `.gitignore` для qmake/build, CI позже.

**Результат этапа:** документ архитектуры (можно прямо здесь расширить) + каркас классов-заглушек,
компилирующийся и связанный с QML через сигналы/слоты.

## Этап 3. Аудиоподсистема — сердце рации (1–2 недели) ⚠️ самый рискованный этап

**Цель:** захват микрофона → кодирование → передача → приём → воспроизведение с задержкой < 300 мс.

### Вариант А (рекомендуемый): GStreamer напрямую
Аврора построена на GStreamer (в ней есть `gst-plugins-good/bad`, Opus доступен).
- [ ] Проверить на устройстве наличие плагинов: `gst-inspect-1.0 opusenc`, `opusdec`, `rtpgsopus`,
      `pulseaudiosrc/sink`, `webrtcbin` (если доступен — сильно упростит жизнь).
- [ ] Собственный pipeline передачи:
  ```
  pulsesrc ! audioconvert ! audioresample ! opusenc bitrate=24000 in-band-fec=1 sprop-stereo=0
           ! opusrtp ! rtppayloadtype ! udpsink host=... port=...
  ```
- [ ] Pipeline приёма: `udpsrc caps=... ! rtpjitterbuffer latency=100 ! opusrtpdepay ! opusdec ! audioconvert ! pulsesink`
- [ ] AEC (эхоподавление): либо `webrtcbin`/`echo-cancel`-элемент, либо аппаратный EC через pulseaudio-module;
      без него динамик+микрофон дают непригодное эхо.
- [ ] VAD/PTT: отправка только при нажатой кнопке; «vox» режим — отдельная опция позже.
- [ ] Маршрутизация: динамик ↔ наушники ↔ Bluetooth-гарнитура (headset profile, HFP vs A2DP —
      для Tx нужен HFP/SCO). Интеграция с `sailfish.mediaservice` Авроры.

### Вариант Б: liblinphone / mediastreamer2 (если портируется)
- Готовый VoIP-стек с jitter buffer, EC, Opus. Тяжелее по размеру, но меньше ручной работы.

### Вариант В: свой RTP поверх QUDP (QUdpSocket) + libopus
- Полный контроль, больше кода: пакетация, seq/timestamp, RTCP, NACK. Только если А и Б недоступны.

- [ ] Замеры: латентность end-to-end, CPU (цель: < 15% на среднем железе Авроры), битрейты 16–32 кбит/с.

**Результат этапа:** два устройства ведут голосовой обмен через тестовый сервер, звук чистый, эха нет.

## Этап 4. Сигнализация и сервер (3–5 дней, параллельно с Этапом 3)

**Цель:** клиент-серверная логика PoC.

- [ ] Выбрать/поднять сервер. Варианты:
  - свой лёгкий сервер: Node.js/Go + WebSocket (signaling) + Mediasoup/Pion для медиаретрансляции;
  - готовый PoC-стек: **Mumble** (мифинг-совместимый, есть Murmur; клиент — свой на Qt) —
    быстро даёт группы/каналы/шифрование;
  - Asterisk/FreeSWITCH + PJSIP, если нужна совместимость с телефонией.
- [ ] Протокол клиента: регистрация (uid/token), список каналов, вход/выход, presence участников.
- [ ] Приоритеты (barge-in): кто говорит, когда говорят двое — правило «первый занял канал»,
      реализация на сервере (lock channel) + статус в клиенте.
- [ ] Шифрование: TLS для WebSocket (wss), SRTP или DTLS-SRTP для аудио (Opus+SRTP через GStreamer `srtpenc/srtpdec`).
- [ ] Resilience: обрыв Wi-Fi↔LTE, reconnect с экспоненциальным backoff, очередь событий на сервере.

**Результат этапа:** полноценный join/leave каналов, список онлайн, корректный barge-in.

## Этап 5. UX рации на QML (1–2 недели)

**Цель:** интерфейс, которым пользуются одной рукой и в перчатках.

- [ ] Главная страница: крупная круглая кнопка PTT (press-and-hold), индикатор состояния канала
      (idle / talking / receiving), имя канала, список участников.
- [ ] Жесты: удержание = TX; двойной тап по экрану = быстрый TX (по желанию); swipe — смена канала.
- [ ] Экран блокировки/фоновый режим: виджет уведомления «Идёт приём…», действие — открыть и ответить.
- [ ] Звуковой дизайн: tonestops («клик» начала/конца передачи), гудок занятости канала,
      play via `GstPlayBin` или `sailfish.mediakit`.
- [ ] История сообщений: авто-транскрибация позже (не MVP); пока — журнал сессий (кто, когда, длительность) в SQLite.
- [ ] Настройки: сервер, позывной, юзернейм/пароль, громкость, шумоподавление, выбор устройства вывода.
- [ ] Темы light/dark, языки (ru/en) через `.ts`-файлы Авроры.
- [ ] Тестирование UI на планшете (Аврора поддерживает разные форм-факторы) и в multi-window.

**Результат этапа:** законченный пользовательский сценарий «включил → выбрал канал → говорит».

## Этап 6. Фоновая работа и надёжность (1 неделя) ⚠️ специфика Авроры

**Цель:** рация принимает вызовы, когда приложение свёрнуто/закрыто.

- [ ] Keep-lock (`native::LockManager`) на время активной сессии — не давать процессу замораживаться.
- [ ] Если freeze неизбежен: рассмотреть systemd-юнит/srv-демон отдельным бинарником
      (фоновый сервис в песочнице Авроры ограничен — изучить `BackgroundService` / `systemd` в SDK).
- [ ] Push-будильники: если собственный сервер — альтернатива интеграция с пуш-сервисом Авроры
      (Aurora Push Service) для «wake-up» уведомлений о входящем PTT.
- [ ] Battery optimization: низкий битрейт в idle, pause signaling ping в экономичном режиме.
- [ ] Оффлайн-поведение: понятные статусы «нет сети / реконнект / выключен микрофон».

**Результат этапа:** входящая передача будит пользователя уведомлением за < 2 сек после открытия канала.

## Риски и как их снижать

| Риск | Вероятность | Митигация |
|---|---|---|
| Freeze фоновых процессов в Авроре убивает приём | Высокая | LockManager, push-wakeup, демон-сервис |
| Нет нужных GStreamer-плагинов на устройстве | Средняя | Проверить на Этапе 3.0; статически доупаковать плагины в .apm |
| Эхо при динамическом режиме | Высокая | webrtcbin AEC / SCO-гарнитура как основной сценарий |
| Латентность > 500 мс через NAT/сервер | Средняя | Relay-сервер ближе к пользователям, small packets, FEC |
| Планшет/смартфон различия UI | Низкая | Harmony UI, адаптивные PageRow |

## Рекомендуемый порядок старта

1. **Этап 0** целиком (окружение + hello world).
2. Параллельно **Этап 1** (API) и **Этап 2** (архитектура + каркас классов).
3. **Этап 3 spike**: за 2–3 дня проверить, собирается ли GStreamer+Opus pipeline на эмуляторе/устройстве.
   Это go/no-go решение всей архитектуры.
4. Затем Этапы 4→5→6→7 итеративно.

Оценка до MVP (Этапы 0–6, базовый UX): **6–10 недель** одному разработчику при полном погружении.
